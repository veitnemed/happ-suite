# Relay Studio: план улучшения рабочего процесса

Актуализировано 1 октября 2026 года по `main` (`422acf5`) и сообщению пользователя: последняя версия приложения открывается и доступна для проверки. План охватывает ежедневное использование, запуск из исходников и выпуск. Переход на PySide6 подробно описан в [UI_PYQT6_MIGRATION_PLAN.md](UI_PYQT6_MIGRATION_PLAN.md).

## 1. Фактическая база

Рабочий интерфейс существует: `src/dashboard.py` содержит страницы VPN, Gemini Web, Antigravity и настроек. Подписка импортируется через `SubscriptionClient`, список узлов загружается, отдельная команда включает Mihomo. Состояния компонентов учитывают намерение, наблюдение и владение. Текущая версия проекта в `pyproject.toml` — `2.3.1`.

Открытие последней версии подтверждено пользователем. Проверка конкретного запущенного файла, всех экранов и живого VPN-маршрута в этой редакции плана не проводилась; для этого нужен паспорт процесса и отдельные результаты сценариев. Старое утверждение о недоступном окне больше не является отправной точкой.

| Точка входа | Что делает код сейчас | Требуемое единое поведение |
|---|---|---|
| Корневой `start.py` / `start.pyw` | Перед запуском вызывает `_stop_old_suite()` и завершает найденный прежний Relay Studio | Повторное открытие показывает окно уже работающего экземпляра |
| `src.start` | Использует mutex и событие `HappSuiteShowDashboard` для показа существующего окна | Сделать основой обычного оконного запуска |
| `run.bat` | Через `scripts/run-hidden.vbs` запускает `src.main` | Ясно обозначить как запуск трея либо направить на оконный вход |
| Установленный пакет | Собирается из entry `start` | Проверить такое же поведение, как у исходного запуска |

Эти различия объясняют, почему «последняя версия открывается» и «повторный запуск безопасен» пока требуют разных проверок. Нельзя выводить версию работающего окна только из текущего Git checkout.

## 2. P0 — предсказуемый запуск и версия

1. Убрать принудительное завершение прежнего экземпляра из обычного открытия корневого `start.py`; использовать существующее событие показа окна. Поведение повышенного запуска VPN проверить отдельно, чтобы не нарушить передачу управления после UAC.
2. Согласовать `start.py`, `start.pyw`, `run.bat`, ярлыки установщика и автозапуск: пользователь знает, когда открывается окно, а когда приложение остаётся в трее. Повторный запуск не создаёт второй контроллер сети и не переподключает VPN.
3. В «О программе» и диагностике показывать версию приложения, build/commit если известен, путь запуска, PID, время старта, режим source/installed и права. Данные фиксируются работающим процессом при старте; обновление Git checkout не меняет его паспорт задним числом.
4. Ясно разделить команды «Свернуть», «Выход из приложения» и «Отключить VPN». Текущий `TrayApp._action_exit()` останавливает монитор и иконки, но не вызывает `stop_all()`; это поведение нужно сохранить при унификации запуска.

**Приёмка:** запуск из исходников и установленного пакета открывает окно, повторный запуск поднимает то же окно без потери VPN и hotkeys, версия на экране соответствует запущенному файлу.

## 3. P1 — ежедневный сценарий VPN

### Первый запуск

Пользователь проверяет Mihomo, вставляет HTTPS-ссылку, нажимает «Сохранить», видит число полученных узлов и выбирает сервер. Затем отдельной кнопкой включает VPN. Интерфейс последовательно показывает: запрос подписки → узлы получены → Mihomo запущен → TUN/маршрут обнаружен → внешний HTTPS подтверждён. Ошибка на любом этапе оставляет понятное действие для повтора; ссылка не попадает в журнал.

Текущий импорт уже получает Mihomo YAML через `SubscriptionClient` и возвращает список узлов. Сохранение подписки не означает подключение. Для завершённого сценария проверять также узлы, выбранный сервер, старт Mihomo и реальный внешний выход.

### Последующее использование

| Действие | Ожидаемый результат | Что требует изменения |
|---|---|---|
| Открыть приложение | То же окно и текущее состояние без сетевой команды | Согласовать точки входа |
| Посмотреть узлы | Список с поиском и понятным активным узлом | Текущий `Combobox` даёт ограниченный обзор |
| Выделить узел | Только меняется выделение в UI | Сейчас обработчик сразу вызывает `select_node()` |
| Применить узел | Явная команда, затем новая проверка маршрута и выхода | Разделить выбор и применение |
| Выбрать лучший зарубежный | Прогресс, предупреждение о возможном переключении и подтверждённый результат | Сейчас алгоритм перебирает proxy через API и может подключить VPN |
| Закрыть окно | Остаётся трей и текущее соединение | Сохранить при новом UI |
| Узнать ошибку | Короткая причина, доступное действие и очищенная диагностика | Объединить сообщения окна и трея |

`choose_best_foreign_node()` меняет активный proxy при проверке кандидатов. В интерфейсе эту операцию нужно описывать как переключение, а не как пассивное измерение. После смены узла прежние IP, страна и задержка теряют статус свежих данных.

## 4. P1 — независимые режимы и состояния

- VPN показывает намерение пользователя, процесс и владельца, TUN/маршрут, внешний ответ и возраст наблюдения. Обнаруженный чужой туннель не даёт права его останавливать.
- Gemini Web показывает отдельно применённый DNS, ответ сайта, регион выхода и статус проверки доступа модели в аккаунте. HTTP-ответ сайта не подтверждает доступ аккаунта.
- Antigravity показывает отдельно установку, запущенный relay и результат проверки работы. Установленный компонент не считается работающим.
- Три горячие клавиши, кнопки и пункты трея вызывают одни и те же команды. При занятой новой комбинации старое сочетание остаётся действующим; результат регистрации виден в настройках.
- Установка Mihomo, VS Code, Antigravity и AG Unlocker остаётся дополнительным сценарием настроек, не обязательным этапом подключения VPN там, где компонент уже установлен.

## 5. P2 — общий контроллер и наблюдение

Сейчас UI вызывает приватные методы `TrayApp`, а периодическое обновление находится в `Dashboard._refresh()`. Извлечь публичные команды в один контроллер для окна, трея и горячих клавиш. Каждая команда получает `operation_id`, этап и итог. Повторные нажатия во время операции обрабатываются по одному правилу; старые ответы не меняют новое состояние.

Периодическая проверка имеет одного владельца. `_check_gemini_now()` сейчас вызывает `_refresh()`, а `_refresh()` планирует следующий вызов через `root.after(1000, ...)`; устранить возможность нескольких цепочек при переносе и проверить один активный таймер. Наблюдение обновляет фактическое состояние, не переписывает намерение пользователя.

Для длительных действий показывать прогресс и конечный результат. Ошибка «Mihomo установлен», «узлы получены» или «сайт отвечает» не должна превращаться в зелёное «VPN подключён» без проверки маршрута и внешнего запроса.

## 6. P2 — проверка и диагностика

Добавить локальный журнал операций с временем, `operation_id`, компонентом, действием, этапом, длительностью, результатом и безопасным кодом ошибки. URL подписки, токены, HWID, конфигурации, ключи relay и секретные части исключать из сообщений, исключений и экспорта. Пользователь видит очищенную диагностику до копирования.

Три уровня проверки фиксировать отдельно:

1. **Автономно:** модели, импорт, ошибки и жизненный цикл на подменных backend; без изменений сети или Task Scheduler.
2. **На рабочем Windows:** открыть все страницы, проверить 150% DPI, повторный запуск, трей, клавиатуру и длинные строки; для сетевых сценариев записать реальный маршрут, внешний HTTPS и восстановление после отключения.
3. **Из пакета:** проверить `onedir`, Setup, старт без консоли, ресурсы, путь данных, hotkeys и обновление установленной версии. `--self-check` проверяет содержимое пакета, но не заменяет открытие окна.

Каждый результат записывать с версией запущенного процесса и средой. Наличие теста, скриншота или успешной сборки не доказывает само по себе работу VPN на Windows.

## 7. P3 — разработка и выпуск

1. Перед правкой смотреть branch, commit и локальные изменения. Не включать в коммит чужие файлы и пользовательские секреты.
2. Для UI вести отдельный preview с вымышленными состояниями; для реальных экранов использовать открывающуюся версию и подписанные снимки. UI-preview не регистрирует hotkeys и не владеет сетью.
3. CI сейчас на каждый push/PR запускает unit-тесты, сборку `onedir`, `--self-check` и Windows Setup. Разделить быстрые проверки и упаковку, сохранив обязательную сборку перед релизом.
4. У выпуска сверять номер версии в исходниках, окне, пакетах и теге. Проверять страницу GitHub Release, Setup, ZIP и контрольную сумму; наличие тега недостаточно.
5. Экспериментальные скрипты из `experiments/` проверять как отдельные прототипы. Их наличие не доказывает восстановление действующей сети после сбоя.
