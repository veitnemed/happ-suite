# Relay Studio: удобный и устойчивый рабочий процесс

Дата: 1 октября 2026 года. Основание: исходники `c4c61b0`, README, текущий скриншот работающего приложения и ограничения пользователя.

Здесь «рабочий процесс» означает и ежедневное использование приложения, и разработку без потери соединения. Переход интерфейса описан отдельно в [UI_PYQT6_MIGRATION_PLAN.md](UI_PYQT6_MIGRATION_PLAN.md).

## 1. Что мешает сейчас

| Подтверждённое наблюдение | Последствие | Следующее действие |
|---|---|---|
| Работающее окно тёмное, checkout уже содержит светлый UI версии 2.3.1 | Непонятно, какая версия реально проверяется | Показывать версию, build и путь runtime |
| `start.py:main()` вызывает `_stop_old_suite()` с `process.terminate()` | Открытие приложения заменяет текущий управляющий процесс | Повторный запуск должен только показать действующее окно |
| GUI получает команды через приватные методы `TrayApp` | Окно, трей и сетевой lifecycle связаны | Выделить общий контроллер команд |
| В `src/dashboard.py` выбор строки вызывает `select_node()` | Просмотр списка может сменить узел при работающем backend | Разделить выбор и применение |
| `_check_gemini_now()` вызывает `_refresh()`, а каждый `_refresh()` планирует следующий | По коду возможно накопление независимых периодических цепочек | Один владелец таймера; подтвердить автономным тестом |
| `src/ui_model.py` и `src/components/view_model.py` уже существуют | Есть основа для единого отображения | Расширять эти контракты вместо новой копии правил в Qt |
| Текущий `TrayApp._action_exit()` останавливает монитор и значки, не вызывает `stop_all()` | Важное поведение можно случайно потерять при миграции | Закрепить отдельные команды выхода и отключения |
| CI сейчас запускает тесты и полную сборку Windows Setup на push/PR | Даже UI-правка запускает дорогой packaging-процесс | Отделить быстрые проверки от выпуска |

Это анализ кода, а не доказательство прохождения сетевых сценариев. Текущую сессию при исследовании не отключали.

## 2. P0 — гарантировать сохранение действующей сессии

### 2.1. Правило этой рабочей машины

Пока чат зависит от Relay Studio, не выполнять stop/restart, смену узла, изменение DNS/маршрутов, обновление runtime, замену исполняемых компонентов и запуск второго сетевого контроллера. Не использовать текущий `start.py` даже «только для посмотреть UI»: он завершает предыдущий экземпляр.

Разрешённый рабочий цикл: чтение исходников → изменения в файлах → автономный preview → mock-проверки → документация результата. Для живых проверок пользователь сам выбирает время, когда можно потерять текущую связь.

### 2.2. Сделать это поведением программы

1. Обычный запуск обнаруживает действующий экземпляр и отправляет команду «показать окно» через уже имеющийся механизм single-instance. Ни `terminate`, ни освобождение hotkeys силой не нужны.
2. Ввести режим защиты сессии в контроллере. Он запрещает сетевые изменения из окна, трея, hotkeys, авто-восстановления и CLI одинаково. Одной отключённой кнопки недостаточно.
3. При защите доступно чтение существующего состояния и журнал. Отказ объясняется: «Текущая сессия защищена; переключение отложено».
4. Обновления скачиваются в отдельный каталог. Замена runtime и компонентов откладывается до явного завершения защищённой сессии пользователем.
5. Сохранить различие между «Скрыть окно», «Закрыть интерфейс» и «Отключить соединение». У выхода явно описать судьбу VPN/relay; не оставлять неуправляемое соединение без способа повторного присоединения.

**Приёмка:** повторный запуск и закрытие preview не касаются production-процесса; тестовый контроллер отклоняет все изменяющие сеть команды при защите. На рабочем VPN эти проверки не разыгрывать.

## 3. P1 — сделать ежедневные действия очевидными

### 3.1. Первый запуск

Один короткий маршрут: проверить Mihomo → вставить подписку → увидеть загруженные серверы → явно подключить выбранный. Сохранение подписки само по себе не включает VPN. Если установка или импорт не удались, введённая ссылка остаётся, показывается конкретная причина и действие «Повторить».

AG Unlocker, VS Code и Google Antigravity не должны быть обязательными для обычного VPN. Установка и факт работы компонента показываются раздельно. Каталог приложения и данные пользователя хранятся отдельно; секреты не попадают в релиз.

### 3.2. Каждое последующее использование

| Намерение | Поведение |
|---|---|
| Открыть приложение | Показать существующее окно, без переподключения |
| Включить VPN | Одна команда, видимый этап и окончательный проверенный статус |
| Посмотреть серверы | Фильтр и выделение не меняют активный узел |
| Найти лучший сервер | Показать прогресс и результат; применять переключение только при явном разрешении и снятой защите сессии |
| Закрыть окно | Скрыть в трей, сохранить соединение и горячие клавиши |
| Узнать причину ошибки | Показать короткую причину и одну следующую проверку; открыть подробности по запросу |
| Включить Gemini Web | Отдельная команда DNS с сохранением прежнего состояния |
| Включить Antigravity | Отдельная команда relay с проверкой реального результата |

Поиск лучшего сервера разделить на измерение доступности и проверку фактического выхода. Текущая `choose_best_foreign_node()` переключает выбранный proxy при переборе; это не безопасная фоновая диагностика для защищённой сессии. До переработки блокировать эту операцию целиком в защищённом режиме. Не делать автоматическое переключение по каждому новому ping.

### 3.3. Горячие клавиши

Три независимых действия: VPN, Gemini DNS, Antigravity. Показывать записанную комбинацию и результат её регистрации. При конфликте новая комбинация не заменяет старую. Кнопка в окне, пункт трея и клавиша вызывают одну команду с одинаковой блокировкой повторов.

Клавиши камеры/Fn могут обрабатываться прошивкой ноутбука. Если приложение не получает событие, объяснить это и предложить сочетание Ctrl+Alt, не обещая поддержку любой аппаратной кнопки.

### 3.4. Статусы без ложной уверенности

- VPN: намерение пользователя, наличие процесса, TUN/маршрут, внешний ответ, узел и возраст наблюдения.
- Gemini: DNS применён, сайт отвечает, страна наблюдена, доступ модели аккаунта проверен либо неизвестен.
- Antigravity: приложение установлено, relay запущен, рабочая сессия подтверждена либо неизвестна.
- После смены узла старые страна/IP/задержка помечаются устаревшими. На экране нельзя оставлять их как свежие.
- «Работает с ограничениями» сопровождается причиной. Зелёный статус не следует из наличия процесса или установки компонента.

## 4. P1 — короткий цикл разработки

### 4.1. Разделить три режима запуска

Следующие режимы — предложения к реализации, **не существующие команды**:

| Режим | Назначение | Граница |
|---|---|---|
| UI preview | Разметка, цвета, состояния, скриншоты | Только вымышленные данные, без production-файлов и глобальных hotkeys |
| Наблюдение | Посмотреть уже собранный снимок runtime | Без команд управления; недоступный runtime не создаётся заново |
| Рабочий runtime | Реальный VPN, DNS, relay | Единственный владелец; явные действия и защита сессии |

В preview отдельно моделировать зависшую загрузку, ошибку подписки, занятый hotkey, недоступный сайт, длинные названия, отказ UAC и отмену. Это даёт полезную проверку UI без разрыва интернета.

Не вводить отдельную службу Windows только ради макета. Сначала выделить контракт контроллера. Отдельный долговечный runtime/IPC рассматривать как следующий шаг, когда понадобится менять UI без замены владельца сетевых операций. У IPC должны быть локальные права текущего пользователя и проверка клиента; не открывать публичный HTTP-порт управления.

### 4.2. Одна задача — один законченный результат

1. Сформулировать наблюдаемую проблему и один критерий готовности.
2. Проверить текущие branch/commit и незавершённые изменения; работать в тематической ветке. При необходимости отдельного checkout использовать worktree, не переносить туда secrets.
3. Изменить ограниченный участок. Не смешивать UI, DNS, обновление движка и упаковку в одном эксперименте.
4. Выполнить подходящие автономные проверки; для UI приложить фактический снимок preview с build и DPI.
5. Зафиксировать результат: что проверено, что работает, что не подтверждено, следующая конкретная проверка.
6. После готовности исходного приложения — пакет и проверка пакета. Коммит/пуш выполнять по согласованной задаче; случайные локальные файлы не добавлять.

Синтаксическая проверка подтверждает только синтаксис. Mock подтверждает контракт, но не VPN Windows. Скриншот подтверждает вид, но не маршрутизацию. Успешный EXE-build подтверждает сборку, но не запуск на другом ПК.

### 4.3. Паспорт работающего экземпляра

В «О программе» и локальном диагностическом отчёте показывать:

- версию приложения и build/commit, если он известен;
- путь запуска, PID, время старта, режим source/installed/preview;
- версию UI и backend;
- статус прав администратора и защиту сессии;
- состояние регистрации каждой горячей клавиши.

Для исходного процесса commit фиксируется при его старте. Обновление checkout во время работы не должно менять показанный build. Если идентификация невозможна, показывать «не определён», а не текущий git HEAD.

## 5. P2 — журнал, который помогает исправлять ошибки

### 5.1. События операций

Структурированный JSONL: `timestamp`, `operation_id`, `component`, `action`, `phase`, `duration_ms`, `result`, `error_code`, `build`. Одно действие имеет один идентификатор от клика/hotkey до результата. Пользовательский текст ошибки отделён от технической записи.

Для переключения нужны этапы: запрос → проверка защиты/владения → подготовка → применение → проверка → успех/ошибка/отмена. Сохранение подписки не должно называться успешным подключением.

### 5.2. Полезная диагностика без раскрытия подписки

Не писать URL подписки, токены, HWID, ключи relay, тела конфигураций и командные строки с секретами. Ошибки `requests` могут содержать адрес: редактировать их до записи. Имена серверов и внешний IP также не включать в публикуемый отчёт по умолчанию.

Кнопка «Скопировать диагностику» сначала показывает очищенный текст. Передавать его куда-либо только по решению пользователя. Скриншоты отчётов делать с закрытым URL подписки; не заменять реальные наблюдения нарисованными результатами.

**Приёмка:** по одному operation_id можно понять, где остановилась операция; проверка с искусственным секретом не находит его ни в журнале, ни в экспорте.

## 6. P2 — сон, восстановление и ошибки

После пробуждения сначала наблюдать состояние, затем обновить UI. В защищённой сессии не выполнять автоматический restart при единичном неуспешном запросе. Отличать отсутствие сети, смену адаптера, отсутствие владельца и недоступный внешний endpoint.

DNS-восстановление должно использовать существующую запись исходного состояния и идентичность адаптера. Не восстанавливать старые значения поверх новых пользовательских настроек и не менять сразу DNS, proxy и маршруты ради одного теста.

Независимый worker/watchdog для будущих разрывных проверок — отдельная работа: mock-восстановление, независимость от родителя, тайм-аут, журнал; затем отдельно разрешённый пользователем live-тест. Наличие скриптов в `experiments/` не означает, что восстановление уже доказано.

## 7. P3 — выпуск после работающей версии из Python

1. Разделить CI на быстрые mock/model/import-проверки и сборку пакета. Для UI добавить автономные снимки репрезентативных состояний.
2. Packaging запускать при изменении зависимостей/упаковки, вручную или для release/tag; обязательную контрольную сборку оставить перед выпуском.
3. Проверять `onedir` отдельно: ресурсы Qt, конфиг, данные регионов, старт без консоли, hotkeys и трей. Затем проверять Inno Setup на чистой Windows.
4. Версия в исходниках, окне, метаданных пакета и release должна совпадать. Подписки и локальные логи исключаются.
5. Не считать tag опубликованным релизом: проверить страницу GitHub Release, наличие ожидаемого файла и контрольную сумму.
6. Обновление действующего экземпляра откладывать до разрешённого времени. Возможность отката хранится отдельно от пользовательской подписки.

## 8. Очерёдность и критерии

| Приоритет | Законченный этап | Проверяемый результат |
|---|---|---|
| P0 | Безопасный повторный запуск и защита сессии | Открытие UI не завершает процесс и не отправляет сетевую команду |
| P1 | Паспорт runtime + автономный preview | Понятно, какая версия открыта; UI можно проверять без VPN |
| P1 | Одна законченная VPN-страница | Импорт, список, состояния и команды понятны на всех preview-сценариях |
| P2 | Единый контроллер и журнал | Действия сериализованы, старые ответы не портят состояние, причина ошибки видна |
| P2 | Отдельно согласованные реальные проверки | Подтверждены маршруты/восстановление, DNS и relay; ограничения записаны |
| P3 | Пакет и публикация | Проверены исходный запуск, frozen-приложение и установщик |

Шаблон записи после этапа:

```text
Этап / build:
Что проверено и в какой среде:
Что реально заработало:
Что не заработало или пока не проверено:
Изменялось ли соединение:
Следующая одна проверка:
```

**Начать с безопасного preview и повторного открытия окна.** Это устраняет ситуацию, когда ради оформления приходится трогать приложение, через которое идёт текущая работа. Следующий этап — один качественно законченный VPN-экран из плана PyQt6.
